## Summary

Trashing and deleting are the two things a file manager can't take back, so they are held to a higher bar than the confirmation preferences alone. This was settled after a copy of the app emptied a home folder with nothing anywhere to say why, and tightened when it happened a second time. What removed the files either time is still not known.

- The delete guard is the set of rules every trash, delete, move and overwrite goes through, wherever it started. It's built and always on.

- The delete test guard is a stricter layer for pre-releases. It asks about every delete and every move, and shows where the job came from. It's on by default through rc.1, and can be turned off in Preferences. From rc.2 it's off by default, but stays in the code as a setting.

- Moving and copying rules, including how links are treated, are in [moving and copying](20260930-145641_moving_and_copying.md).

## Specification

- Home, any folder above it, and the top of a mounted drive or share are never trashed or removed, whatever asked.

- One job may not take most of what sits directly in home. It's refused, not asked about.

- Removing a folder tree never follows a link of any kind. The link is removed as a link. This is not a setting.

- Nothing outside a window can trash, delete, move or empty the trash.

- Only the trash and delete commands in a window count as a person asking. Anything else always asks.

- A job of `confirm-many-items` or more asks, even with confirmation off. 20 by default, and 0 turns it off.

- Every question that can remove files starts on Cancel.

- A trash or delete key within a second of a window appearing or taking focus is ignored.

- Every trash, delete and empty trash writes one log line, and on Linux the same line goes to the system journal.

- The test guard:
	- On by default, through `debug.testguard-all-deletes` in the settings file. Off by the checkbox at the end of Trash on the Behavior page.
	- The `NEMO_TESTGUARD_ALL_DELETES` environment variable beats the setting either way.
	- A build can also be compiled with it forced on. Then nothing turns it off, and the checkbox is grayed out.
	- It stays in rc.1, and the changelog and release notes say so and where to turn it off.
	- From rc.2 the setting's default is off. The code and the setting stay, so it can still be turned on.

## Goals

- Make it hard to lose a file by accident, even where that makes the app less convenient than its ancestors.

- Leave a record of every trash and delete that survives losing the home folder.

- Hold every path that removes files to the same rules, including ones no dialog ever sees.

### Non-goals

- Protecting a person from their own other programs. Anything that can write the settings file or talk on their session bus can already do what it likes as that user.

- A setting to follow links when deleting.

## Design

### Where the rules are checked

- The guard is checked where each file is actually removed, not at the dialog. So a path that never shows a dialog is held to it too.

- Home, the folders above it and mounted drives and shares are matched by file identity, not by name. On Windows that catches home by its short 8.3 name, and through a junction.

- A delete that reaches a mount inside a folder stops there instead of emptying the drive.

- Windows reports a junction as an ordinary folder, so every walk that removes things asks one shared check whether it's really a folder or a link. The lint gate fails a new walk that doesn't. That covers a symlink, a junction, a `.desktop` file and a `.lnk` shortcut, wherever one sits in the tree.

- `cicd/utility/lint-c.bash` keeps three lists: the files allowed to start a trash, delete or move job, the bus methods, and the files allowed a raw delete. That last list only touches the app's own files, such as the settings on `--reset`, the thumbnail cache and old crash reports.
	- Every delete in the file operations goes through one wrapper that checks the guard. The lint gate fails one that doesn't.
	- An overwrite can't be set up without the question above it. The lint gate fails one that is.

### Who is asking

- Nothing outside a window can trash, delete, move or empty the trash. Each of those starts from something done in a window: a command, a drop, undo, or a button in the preferences. The bus interface that let other programs copy, move and empty the trash came from the Nemo desktop, and was removed. Only the freedesktop one is left, and it shows folders and properties.

- Only the trash and delete commands in a window count as a person asking. Anything else, such as undo or a drop, always asks first whatever the preference says, and the question says so. The caller says which it is. The input event behind it is kept for the log.

- Only the Empty Trash command in a window may skip its question, whether from the menu, the trash bar or the sidebar.

- A job of `confirm-many-items` or more asks even with confirmation switched off. A slip that takes one file is a nuisance; one that takes a folder is a day.

- A job that would take most of what sits directly in home is refused outright, not asked about. Nobody clears a home folder from a file manager on purpose, and a question is one Enter away from yes.

### Questions and keys

- Every question that can remove files starts on Cancel. The dialog was meant to be the pause, but a stray Enter goes straight through a pause.

- A trash or delete key that arrives within a second of a window appearing or taking focus is ignored. A window that opens while someone is typing somewhere else gets the rest of that typing.

- "Ask before moving files to Trash" is on by default.

### What is logged

- Every trash and delete job writes one line: how many items, which folder, the first item, the window, whether a trash or delete command asked for it, and the key or button behind it. Every refusal and every empty trash writes one too.

- On Linux the line also goes to the system journal, under `nemo-anywhere`. The usual place for a log is a file under home, which is the first thing lost, and a rollback of home leaves the journal alone.

### Moves and overwrites

- A move on one filesystem is a single rename, and an overwrite happens inside the toolkit, so neither would reach the delete path on its own. So a move job asks once up front, with the test guard on, naming the destination and every source about to leave. An overwrite asks per file, naming the target whose contents are lost and the source replacing it.

- Links are always moved as links. See [Moving](20260930-145641_moving_and_copying.md#moving).

- Removing a template in Preferences goes to the trash through the same job as any other, so it asks and is logged.

### The test guard

- With it on, every delete, trash, empty trash and move asks, and shows the paths and where the job came from. The ordinary questions it replaces stay out of the way, so nothing asks twice. A drop that moves files doesn't ask its own question then. A copy still does, since the guard doesn't cover copies.
	- The "can't trash, delete instead?" and conflict questions need a real choice, and still come up.

- Every guard dialog has a short note under the headline. It says the guard is used for all pre-releases, isn't needed for this release candidate, and where to turn it off.

- The dialog is only as big as its text. It's capped at half the screen's shortest side and a quarter of its longest, and takes width before height, so long paths don't wrap. The headline keeps about 30 characters to a line. The paths and the call stack scroll, and the buttons have their own row under them that never scrolls or goes off screen.

- While it waits for an answer it pauses the job that asked, so the job's progress window doesn't come up over it.

- The demo turns it off, and its lint checks that.

### Open questions

- Whether ordinary delete and overwrite questions go back to OK as the default once the test guard is off. See [Superseded](#superseded).

- The guard's dialog resumes a job the user had paused. It should only resume what its own pause stopped (2026092813381438).

## Alternative ideas

### Unconsidered

- A trash that keeps a short undo window even for a delete that skips the trash.

### Rejected

- Following links when removing a tree, even as a setting.

- Deciding "a person asked" from whether an input event was in flight. Any unrelated key or click could count.

- Asking, rather than refusing, when a job would empty most of home. The question is one Enter away from yes.

- A test guard only in debug builds. A shipping build has to be able to arm it too.

- Taking the test guard out of the code once pre-releases are done with it. Only its default changes, at rc.2.

### Superseded

- The confirmation dialogs keeping their usual default button, with the dialog as the pause (2026-09-07). Every question that can remove files starts on Cancel since 2026-09-14.

- A deferred item would reverse that and put OK back as the default, once the app has been in reliable use for many days or weeks, archiving included. The guard's own detailed dialogs stay either way.

- The test guard armed by a define in the code. The define is 0 now, and the setting arms it, on by default.

- The bus interface for copy, move and empty trash, from the Nemo desktop. Removed.

## Research findings

- A move on one filesystem is one GIO call, and an overwrite happens inside GLib. Neither goes through the app's own delete path, which is why moves needed their own question.

- Windows calls a junction a plain folder. Three walks trusted that and would go into one: deleting a folder from the Recycle Bin, replacing a folder on a copy, and an empty trash walk. The first really deleted what a junction pointed at.

- The app's own log was in the home folder that went, both times. Nothing else on the machine said what did it.

## Roadmap

- rc.1 keeps the test guard on, and says so in the changelog and release notes.

- rc.2 turns the test guard off by default. The setting still turns it on.

- Then settle whether ordinary questions go back to OK.
