## Summary

Settings are one text file and one window. The file is the record. The window is a way to change it, and so is a text editor.

- Built today: the settings file, live reload, changes shared between running copies, and a Settings window with a tab list down the left and sub-tabs under Views and Behavior.

- Planned before the next cut: the tabs regrouped under 2 parent tabs, User interface and Advanced. Also new size settings, an image thumbnails section, numbers with their units inside the field, search, a Keyboard tab, and Blake3 checksum options.

- How the settings store fits the rest of the app is in design.md, under [Configuration and persistence](../design.md#configuration-and-persistence). The rule for code that listens to a settings group is under [Handlers on settings groups](../design.md#handlers-on-settings-groups).

## Terms

- Setting: one value that can be changed, such as whether to shade every other row.

- Settings file: `settings.shcl`, where every setting that isn't at its default is stored. See [The settings file](#the-settings-file).

- Key: a setting's name in the settings file, written `group.key`, as in `list-view.column-fit-percent`. The group is the part before the dot.

- Default: the value a setting has when nothing is stored for it. Defaults live in one table in the code.

- File-only setting: a setting with a key and a default, and no control in the Settings window.

- Settings window: the window opened from Edit, Settings, or with Ctrl+,. It was called Preferences until it was renamed.

- Tab list: the list down the left side of the Settings window.

- Tab: an entry in the tab list, and the page of controls it shows. Clicking a tab shows its page.

- Parent tab: a tab with sub-tabs under it.

- Sub-tab: a tab listed under its parent tab, indented one step per level.

- Section: a titled group of controls on a tab. The title is in bold.

- Control: one thing on a tab that changes a setting or does something. A checkbox, a dropdown, a spin box, a text field, or a button.

- Spin box: a number field with minus and plus buttons beside it.

- Unit: the text after a number that says what it counts, such as `%`, `GiB`, or `days`.

- Tooltip: the text shown when the pointer rests on a control or its label. Older notes call it flyover tip text.

- Views: the 3 ways the content view lists a folder, and a fourth one planned.
	- Detailed view: rows with columns. It's called List view today, in the app and in older docs.
	- Compact view: names in columns that run sideways.
	- Icon view: a grid of icons with captions under them.
	- Image thumbnail view: planned. Today a folder that's mostly images opens in icon view at a bigger size, adn that isn't a view of its own.

- Default and Current: the 2 sub-tabs of the view settings tab. Default edits the defaults every folder starts from. Current edits the settings saved for one folder. See [Default and Current](#default-and-current).

- Layouts below use these marks:
	- `[ ] Label` is a checkbox.
	- `[Label]` is a button.
	- `Label [ 50 % -+]` is a spin box showing 50, with its unit inside it.
	- `[nothing]` is a dropdown entry that leaves a line empty.

## Specification

### Built today

- Every setting is in one text file that can be edited by hand. An edit made while the app runs takes effect at once, as if made in the Settings window.

- The file stores only values that differ from their default. Everything else is listed at the end, commented out, with the value in use.

- A change made in one running copy shows in every other copy at once.

- The Settings window opens big enough for its largest tab, up to 9 tenths of the screen.

- The tab list shows sub-tabs indented under their parent tab, all the time. A parent tab and the sub-tab it shows are both lit.

- Tabs never take the keyboard focus. Ctrl+Page Up, Ctrl+Page Down, Ctrl+Tab, and Ctrl+Shift+Tab step through the tabs and sub-tabs in list order, and wrap.

- Settings that only exist on Windows are on a Windows tab, which the other platforms don't have.

### Planned before the next cut

- The window title is "Settings - Nemo Anywhere".

- More space between sections, and a narrower content area, now that the window doesn't need its old width.

- Tabs regrouped under 2 parent tabs, User interface and Advanced, as under [Planned tabs](#planned-tabs). The Windows tab stays, between them.

- Every number with a unit is right-aligned in its field, with the unit inside the field, after the number.

- A search field at the top of the window that doesn't scroll away.

- A Keyboard tab where shortcuts are shown, changed, and reset.

- A Blake3 checksum section on the Advanced tab, in Cache.

- New size settings for text in the Compact view, Detailed view, Places, tree view, and the Settings window itself. Icon size is only set for Icon view.

- In the Settings window a button sits at the left, on a line of its own.

- An Image thumbnails section, and Image thumbnail captions, for the planned fourth view.

- The Default and Current sub-tabs built from one definition, so they can't drift apart.

## Goals

- One place for every setting, readable and editable by hand, that behaves the same as the window.

- A window where every setting can be found, either by its place in the tab list or by search.

- No tab that opens behind a scrollbar.

- A setting's purpose is clear from its label and tooltip, without a manual.

### Non-goals

- Settings from a pre-1.0 install aren't moved over, since nothing is left that can read the old store. Keyboard shortcuts are the one exception.

- Import and export of settings. The settings file can be copied as is.

## Design

### The settings file

- The file is `settings.shcl`, in the folder the platform keeps per-user settings in: `~/.config/nemo-anywhere` on Linux and the BSDs, `%APPDATA%\nemo-anywhere` on Windows, and `~/Library/Application Support/nemo-anywhere` on macOS. A folder left by an older build is moved on first run.

- Only what was chosen is stored. A value equal to its default is dropped, so the file stays short and a later change to a default still reaches the user.

- Everything unset is listed at the end, commented out, with the value in use. A one-line note is added wherever the key doesn't explain itself. Uncommenting a line is the same as changing the setting in the Settings window.
	- Keys the app writes back itself are left off that list, since a hand edit would only be overwritten. Window size, sidebar width, and the last state of a search toggle are examples.

- An edit made while the app is running is picked up straight away.
	- A save reads the file first. A hand edit the app hasn't picked up yet is taken in, and a setting changed both ways keeps the change made in the app, the same as when the edit is picked up first.
	- A file removed by hand goes back to defaults, apart from changes made in the app and not saved yet.

- A change made in one copy shows in every other running copy at once. It goes to them the way a tab move does, not through the file, so nobody waits for the save and the file watch.
	- The copy that made a change saves it. The others hold it in memory until the file has it, so a change is one write, not one per copy. A copy that saves for a change of its own writes what it holds as well, which is what the others would write.
	- Each change has the time it was made. 2 copies that change one setting at the same moment both keep the later one. If the copy that lost had saved its own already, the one that won saves again.
	- Going back to the default goes over as a removed line, the same as in the file.
	- A copy that is still starting, and not in the list of copies yet, gets the change from the file after the save. A copy that quits tells the others what it hasn't sent, then saves. One that crashes before its save leaves the change only in the others' memory, and the next of them to save a change of its own writes it.
	- The file watch stays, for hand edits. A change that already came over isn't taken again when the file catches up, so its handlers run once.

- The file ends with SHCL's info block, which names the format it was written in.
	- A file in an older format is copied beside it as `settings_backup_<YYYYmmDD-HHMMSS>_format-v<N>.shcl`. A new `settings.shcl` is written with the settings this release knows, converted by SHCL.
	- A file with no format line is read as 2.x at startup, since no file a 2.x release wrote has one. It's rewritten when today's rules would read it differently.
	- The cost is a hand-written file the app never saved, which has no info block either. An unquoted backslash in it, as in `C:\temp`, is read the 2.x way, and the file as written is in the backup.
	- A file with no format line that turns up while the app runs is a hand edit, and is read by today's rules, unless the 2.x file from startup couldn't be saved over yet.
	- A file in a newer format is used and never saved over, so an older build doesn't undo a newer one's settings.

- Types, defaults, and allowed values live in one table in the code. A matching schema sits beside the app, so `shcl check --schema` can catch a typo in a hand-edited file.
	- Keeping defaults in one place goes against the SHCL library's advice to give a default at each read. With nearly 200 settings, many read from several places, 2 reads that disagree about a missing value are a silent bug.

- A few settings are the desktop's to decide: which terminal to open, whether the session remembers recent files, and 12 or 24 hour clocks. Where a desktop publishes them its answer is read, and everywhere else our own value stands in. That is the only use left of the desktop settings database. It's read only, and never touches a schema of ours.

- Some settings are file-only. They have a key and a default, and no control.

- On Windows, a path in a setting is taken as written. A backslash is a path character, never an escape. The rule for every file a user writes is in design.md, under [Paths and desktop settings](../design.md#paths-and-desktop-settings).

### Keyboard shortcuts file

- Keyboard shortcuts are kept beside the settings file in `accels`, in GTK's own format.

- Upstream Nemo keeps its shortcuts in `~/.gnome2/accels/nemo`. The first start with no `accels` reads that file, so custom shortcuts come over, and writes `accels` straight away.
	- That `accels` exists is what marks the old file as read. So it's read once and never written.
	- `--reset` empties `accels` rather than removing it, for the same reason.

- The planned [Keyboard tab](#keyboard-tab) edits this file.

### Command line settings

- Where a setting is a command line for another program, the parts the app fills in are written `{{LIKE_THIS}}`, capitals between double braces.

- Braces were chosen because nothing expands them. The same line pasted into a shell or a command prompt to try it out comes back unchanged. `%NAME%` would vanish on Windows, and `${NAME}` on Linux.

- Only the markers a setting declares are replaced. Anything else in braces passes through as itself, so there is nothing to escape.

### The window

- The Settings window opens the size of its longest tab. It measures every tab and opens tall and wide enough for the largest, up to 9 tenths of the screen, so no tab starts out behind a scrollbar.
	- A tab too long for that is split into sub-tabs of related settings, as Behavior is.
	- Its smallest size is written for a 96 dpi screen and scaled by the display's font scaling, so it means the same thing at 150% as at 100%.
	- A tab still scrolls on a screen too small for it.

- The tab list replaces GTK's own page list, which can't nest. It draws with the same theme rules.
	- A sub-tab is indented one step per level, at any depth.
	- A parent tab and the sub-tab it shows are both lit, at every depth.
	- Every sub-tab is always listed, and a parent tab opens the sub-tab it showed last. A parent tab with a page of its own, such as the planned Advanced, shows that page.

- Tabs never take the keyboard focus. A click switches tabs and leaves the focus where it was, and Tab passes over the tab list.
	- Ctrl+Page Up and Ctrl+Page Down, and Ctrl+Tab and Ctrl+Shift+Tab, step through the list in order, sub-tabs included, and wrap. Back from a first sub-tab goes to the last sub-tab of the tab before. Hidden tabs are skipped.
	- The rule for tabs in every window is in the [UX style guide](../style-guide_ux.md).

- A grayed tab still opens, and shows its controls grayed out, so it's plain what is off. Its page is never blank. Current, with Remember per-folder settings off, is the one case today.

- Settings that only exist on Windows are on their own Windows tab, and in a `windows` group in the file. The tab isn't built into the other platforms' Settings windows at all. The keys still take effect if hand-edited anywhere. It's the tab that is Windows-only, not the settings.

- A button that acts on a tab's content sits at the top right of that content, never in the tab header. Planned: in the Settings window it sits at the left instead, on a line of its own at the top of the section it acts on. At the top right it sat oddly beside the nested tab list, and made the whole window wider.

### Default and Current

- Default edits the defaults every folder starts from. Current edits the set saved for the folder in the last focused window, and applies a change to that window at once.

- Current is grayed out while Remember per-folder settings is off. It still opens, and shows its controls grayed, under the folder's path. Turning remembering off while Current is showing leaves it showing, grayed.

- Current shows both icon sizes, the one for an ordinary folder and the one for a folder that is mostly images. The pair is what a child folder inherits, so a size the folder itself won't use is still worth setting.

- Built today: Default and Current are 2 copies of the same controls in the layout file, kept in step by hand. Each has a button that copies to the other, and Current has Forget, which drops the folder's saved set.

- Planned: both are built from one definition, with the same controls, text, and layout. Only the values behind them, and whether they're enabled, differ.

- Planned first section on each:
	- Default: `[Copy settings to Current]`, at the left.
	- Current: `Current folder: "<folder name>"`, and under it `[Copy settings to Default]  [Forget]`, at the left.

- Planned sections on each, after View and Icon view:
	- Image thumbnails, to the right of Icon view. It settles how a folder that is mostly images opens.
		- `[ ] Enable automatic switching`, with a tooltip. Today this is `[ ] Show folders of pictures in icon view`, under Icon view.
		- `Images threshold [ 50 % -+]`, with a tooltip. The share of files that must be images. Today it's file-only.
		- `Thumbnail size [ 500 % -+]`. Today this is `Mostly images (%)`, under Icon view.
	- Compact view: `Text size [ 100 % -+]`, as a percent of the system's UI font size, and `[ ] All columns have the same width`. Its icon size goes.
	- Detailed view: renamed from List view, and placed to the right of Compact view, lined up with Image thumbnails above it. `Text size [ 100 % -+]`, as a percent of the system's UI font size, in place of its icon size.

- Icon size is only on Icon view. In Compact and Detailed view the icon follows the text size, and Zoom In and Zoom Out change Text size, a percent under or over the desktop's text size. Today a list row's text grows with its icon size, as under design.md's [Icon sizes](../design.md#icon-sizes).

### Search

- A search field at the top of the window, in an area that doesn't scroll.

- Matches are listed in 3 groups, in this order:
	- Labels that contain the text as typed.
	- Aliases, other words a setting is known by.
	- Fuzzy matches, ranked lowest.

- Aliases are metadata on each setting in the SHCL schema files, read in when the app is built.

- A fuzzy match works like fzf. The letters typed have to appear in the label in order, not next to each other, and case doesn't matter. The fewer the gaps, the higher it ranks. With the matched letters in brackets:
	- `open` matches `[Open] in another universe`, as typed.
	- `new` matches `Open every [new] folder underwater`, as typed.
	- `Andies` matches `[A]ctually, [N]OBODY [dies]`, as a fuzzy match, ranked low.

- Each match shows the path to the setting, from the tab down, as in `<tab> ⏵ <sub-tab> ⏵ <setting>`. There are as many levels as the setting has.

- The letters that matched are bold, larger, and in a different color that suits the theme.

### Blake3 checksum section

On the Advanced tab, in Cache, after Thumbnail cache.

- `[ ] Cache whenever files require a full-read anyway.`
	- Tooltip: "Highly recommended. Note: Always enabled for thumbnail cache operations, unless that feature is turned off."

- `[ ] Persist across hosts via xattrs.`
	- Today's `[ ] Save checksums onto the files`, moved from Preview and relabeled. Same key, `file-cache.save-checksum`, and still off by default.
	- On Windows the label says alternate data streams, since that's what is written there. Only local NTFS and ReFS drives keep them.
	- New: disabled while the checkbox above is off. Today it doesn't depend on anything.
	- Tooltip, with its pros and cons:
		- Pro: it's a cheap way to tell unique or changed content apart, that works across platforms and hosts.
		- Con: not every file tool or filesystem keeps xattrs.
		- Con: it can throw off the rare file tool that relies on ctime. Most use mtime, which this doesn't change.
		- Con: some filesystems limit the total xattr size per file.

- How checksums are kept on files today is in [20260930-145641_file_cache.md](20260930-145641_file_cache.md#checksums-on-the-files).

### Shortcut extension checkbox

- Today one checkbox, key `preferences.show-shortcut-extension`, decides whether a shortcut's extension counts as part of its name. It's on every platform.
	- On Windows it reads `Show the .lnk and .desktop extensions in a shortcut's name`, since both kinds of file are shortcuts there.
	- Elsewhere it reads `Show the .desktop extension in a shortcut's name`.

- Planned: the same key, under User interface, General, Shortcuts.
	- On Windows: `[ ] Show the .lnk extension in a link's name`. It still covers `.desktop` too, which the label no longer says.
	- Elsewhere the label stays about `.desktop`, with "link" in place of "shortcut".
	- "Link" can also be read as a symlink, which this checkbox doesn't touch.

## Alternative ideas

### Unconsidered

None.

### Rejected

- Letting Behavior scroll, and sizing the window to the next longest tab. Sub-tabs were chosen, so no tab starts behind a scrollbar.

- Keeping GSettings as an API over a new backend. It still needs a compiled schema to build and install on every platform, which is what the settings file got rid of. See design.md, [Configuration and persistence](../design.md#configuration-and-persistence).

- Defaults given at each read, as the SHCL library suggests. See [The settings file](#the-settings-file).

- Listing a parent tab's sub-tabs only after it's clicked, until it's clicked again. Every sub-tab stays listed.

- `%NAME%` and `${NAME}` markers in command line settings. See [Command line settings](#command-line-settings).

### Superseded

- "Preferences" as the window's name. It's "Settings" now, everywhere a person sees it.

- Default and Current as tabs on top of the Views tab. They're sub-tabs in the tab list now, so one window doesn't have 2 kinds of sub-tab.

- Current refusing to open while Remember per-folder settings is off. It opens on grayed controls now.

- Icon size on Compact view and List view. Planned to be replaced by Text size.

- Buttons at the top right of a tab in the Settings window. Planned to move to the left.

## Research findings

- GTK's own page list can't nest, which is why the tab list is drawn by the app.

- On a 1920x1200 screen, splitting Behavior into 3 sub-tabs took the window's opening height from 1080 to 774, with no tab needing a scrollbar.
