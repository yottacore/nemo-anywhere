## Summary

The file cache is built and in use. It is a private SQLite database under the user's cache folder, with what has been worked out about files on disk, so it doesn't have to be worked out again. Thumbnails are the first thing in it and the reason it exists, but its tables are about files rather than pictures.

- How thumbnails are made, stored and shown is in [thumbnails](20260925-063617_thumbnails.md). The overall design is in [design.md](../design.md).

## Specification

- One SQLite file under the user's cache folder, linked into the program.

- Three tables of data: `files` for each distinct content, `paths` for each uri, and `thumbnails`.

- Checksums are blake3. A checksum can also be written onto the file itself, in extended attributes or a Windows alternate data stream. This is a setting, off by default. See [Checksums on the files](#checksums-on-the-files).

- A damaged database, or one written by another version of the tables, is thrown away and rebuilt.

- Pruning keeps it under a size limit and an age limit, on a worker thread.

- The app never visits a network share on its own to fill it in. Only something a person does reaches a share.

## Goals

- Know a file again after it's been renamed, moved or copied.

- Do slow work once. A hash or a thumbnail made for one copy serves every other copy of the same content.

- Never hold up the window, however briefly.

### Non-goals

- Needed to run. With no database, or a damaged one, the app still works. It just does some work over again.

- A crawler. It doesn't walk the disk on its own to fill itself in. It learns from what the app is already doing.

## Design

### Tables and storage

- SQLite is linked static. It has to come through pkg-config rather than meson's `find_library`, because the cross sysroot is not on the compiler's own search path.

- Three tables of data, plus one row of bookkeeping for pruning. `files` is one row per distinct set of file contents: the size, and the checksum once anything has bothered to compute one. It stores no image, picture or not. `paths` is one row per uri, pointing at the file it belongs to and carrying its own timestamp. `thumbnails` is only for images; it hangs off a `files` row and keeps the encoded image.

- Splitting paths from files is what lets a file that moved, or a second copy of one, find a thumbnail that is already there. Every file seen is a `files` row, and the copies of one are the paths hanging off it. A file nothing can draw has no `thumbnails` row and is otherwise an ordinary record.

- A checksum settles what two records that looked separate really were, so learning one folds them together. The image and every other name move onto the record that stays. Without a checksum, size and timestamp together are the only guess available, and two unrelated files that happen to match both would share a thumbnail.

- A record is found by its checksum alone, as the checksum is what is unique. One found at another size had its size taken before an edit, and the newer size replaces it.

- Every launch is its own process and several can be open at once, so the file is in WAL mode with a busy timeout. Writes are small and the whole store is rebuildable, so `synchronous` is NORMAL rather than FULL. A power cut can cost the last few rows, which is not worth an fsync per row.

- A damaged file, or one written by another version of the tables, is thrown away and rebuilt at open rather than migrated or repaired. Nothing in it can't be worked out again from the disk. Damage noticed while running only stops the store being used, because deleting a file other processes still have open is worse than going without until the next launch. It also leaves a marker beside the file, and the next launch starts over when it sees one. A damaged page deep in the file does not stop it opening, so without the marker nothing would ever act on it.

- A version that could not be read at open, such as on a file that stays busy past the wait, is neither damage nor another version. The file is left alone for the copies that have it open, and that copy runs without the cache.

### Keeping it small

- Draw counts are kept in memory and written in one transaction. Scrolling a big folder draws the same file repeatedly, and the age rule works in days, so a write per draw would buy nothing.

- The window's thread never touches the file. Another copy can hold it for seconds, during a prune or a long write. Draw counts and a refresh asked for by hand are queued, and a thread of their own writes them: the counts after 30 s or once 256 files are waiting, a refresh at once. A refresh that is still queued is done first by the next read or write of a thumbnail, so the old picture is never read back. A write that fails is tried again after the same 30 s, and a clean quit writes what is left.

- Pruning runs on a worker thread over a connection of its own, so it never holds up a draw. Each pass checks the file for damage, forgets local files that are gone, forgets names left with no thumbnail, drops thumbnails not drawn for too long, then drops the least recently drawn until the file is under its size limit, and last hands the freed space back to the disk.

- A file is only forgotten when its folder is still there. A whole folder missing is more often a drive that is not plugged in. Shares are skipped, and so is any folder that is slow to answer, since one that is not answering costs about twenty seconds per question.

- A name whose file no longer has a thumbnail keeps only a size, a time and maybe a checksum, and the file gives all of those again when it is next thumbnailed. It is forgotten once nothing has been stored under it for as long as the age limit, or 180 days with the age limit off. The file record goes too once no name points at it. A name that still has a thumbnail is left to the thumbnail rules. Nothing indexes when a name was stored, so these are picked without holding the write lock, and each delete checks again.

- A pass is due at random between 4 and 24 hours after the last, and waits until nothing has been drawn for 5 minutes. All three are in the config file. Whoever finishes a pass picks the next time and writes it in the file, so every copy running agrees on it.

- Only one process prunes at a time. The claim is a row in the database, taken in a write transaction, so SQLite's own locking decides who wins. That works the same on every platform, where a lock file would need a separate answer for Windows. The claim carries a heartbeat, and one nobody has touched for ten minutes belongs to a process that died and is taken over.

- Both rules go by a thumbnail's age, the later of when it was made and when it was last drawn, and that age is indexed. Each batch is picked under the write lock, so it walks the index rather than sorting the whole table while other windows wait to write.

- A batch ends after 256 thumbnails or about 1 MB of them, whichever comes first. Deleting a big thumbnail takes longer than a small one, so without the byte limit a batch of big ones would hold the write lock for much longer.

- The space goes back a few pages at a time with incremental vacuum rather than a full VACUUM. A full one keeps the write lock for as long as it takes to copy the whole file, and every other copy would wait on it.

- Quitting stops a pass part way through, and it lets go of its claim.

- The settings are on the Preview page: the size limit, the age limit, forgetting missing files, and saving checksums onto files. The schedule stays in the config file only. The page also shows how many thumbnails there are and the space on disk, with a button to clean up now and one to empty the cache.

- Emptying asks first, then drops every row and runs a full VACUUM. In WAL mode the VACUUM writes the new file into the journal, which then takes up more than the old file did, so the journal is folded back in and cut short after it.

### Checksums on the files

A checksum can also be left on the file itself, in three attributes: the checksum, and the size and time it was taken at. That way it travels with the file. A copy onto another machine, or onto a drive this program has never seen, arrives already knowing what it is.

- On Linux and the BSDs they are extended attributes in the `user` namespace. On Windows they are alternate data streams, which only NTFS and ReFS have, and the setting says so where it is switched on.

- It is off by default, and switched on by a setting. Writing an attribute changes the file's ctime, which can trick poorly-written backup programs into backing up unchanged content again.
	- On Linux, the BSDs and macOS, ctime can't be reset. The kernel sets it on any attribute write, and there is no call to set it back.
	- On NTFS a write to any stream counts as a change to the whole file and moves its modified time. Left alone, that would make each checksum stale as soon as it was written, and the file would read as edited to everything else too. The write tells its handle to leave the file times as they are.

- With it on, a checksum is written when a thumbnail is made, so files already in the cache get one the next time they are drawn. A file that already carries the same checksum is left alone.

- The time is written last of the three, and reading requires both the size and the time to match. A write that stops part way then leaves the old time next to the new checksum, and the next reader throws the lot away. Written the other way round, a half-finished write leaves the old checksum under a size and time that both match, which no reader can catch.

- Writing an attribute is slow enough that it happens after the database is already up to date, never in front of a draw. A filesystem with nowhere to put one simply goes without, and the database still knows.

## Alternative ideas

### Unconsidered

None.

### Rejected

- A lock file for the prune claim. It needs a separate answer on Windows. A row in the database works the same everywhere.

- `synchronous` FULL. An fsync per row isn't worth it for a store that can be rebuilt.

- A full VACUUM after each prune. It keeps the write lock for as long as the whole file takes to copy.

### Superseded

- Staying with the shared freedesktop thumbnail folder. See [thumbnails](20260925-063617_thumbnails.md#superseded).

## Research findings

- An attribute write sets ctime on Linux, the BSDs and macOS, and there's no call to set it back. On NTFS a stream write moves the file's modified time unless the handle is told not to.

- A prune batch of 256 thumbnails, with 40 thousand of 16 KB in the file, made another window's store wait up to about 1.4 s. Bigger thumbnails make each batch longer (2026093010493420).
	- Measured again on 20261003 with the byte limit in. The longest waits, 1 to 1.4 s, come from the space being handed back. Each step there holds the lock for only about 40 ms, but the steps follow one another with no gap. A waiting store sleeps up to 100 ms between tries, so it keeps waking while the next step has the lock (2026100319191870).

- While another copy pruned 40 thousand thumbnails of 16 KB, a window drawing and loading thumbnails had its own thread wait on the cache up to 2.3 s at a time, 55 s out of 60. With a hundred pictures drawn instead of two thousand, up to 0.5 s at a time. Its thumbnail threads waited on the prune and held the store's lock meanwhile, and a draw count needed that lock. Since 2026092813381436 the longest call on the window's thread took 0.3 ms in the same runs.
