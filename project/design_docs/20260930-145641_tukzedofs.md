## Summary

TukzedoFS is a database of what nemo-anywhere knows about files. It sits beside the real filesystem and never replaces it. It's a filesystem about files: where each one is, its size and dates, what its content hashes to, and which files are really the same content.

- It grows out of the file cache that stores thumbnails today. Thumbnails were the first use. Finding and deduping copies, tags, and the size scans in the compress, copy and move dialogs come next.

- Any file whose whole content passes through the app's memory is logged with a hash. Every other file gets only what is cheap to learn.

- PostgreSQL is used where one is available and chosen in the settings. SQLite is used otherwise, and is what dogfood builds are tested with.

- Status: the file cache is built and in use, on SQLite. The rest of this doc is design, and not built yet.

- Most of TukzedoFS, the WinFS-style features included, will probably go in [Captain Nemo](https://github.com/t00mietum/captain-nemo) rather than nemo-anywhere. It's documented here anyway, and that could change. PostgreSQL is the least likely to come here.

- The uses built on it have their own docs: [dedupe and thumbnails](20260925-063617_dedupe_and_thumbnails.md), [compression](20260929-101432_compression.md), and [moving and copying](20260930-145641_moving_and_copying.md). The overall design is in [design.md](../design.md).

## Specification

- TukzedoFS is its own database, kept beside the files. Nothing is mounted, and no file content is stored in it.

- Where it's kept:
	- PostgreSQL, when one is available and chosen in the settings.
	- SQLite otherwise. It needs no setup, so it is the default.
	- Dogfood builds are tested with SQLite.

- What gets logged:
	- Any file whose whole content passes through the app's memory, and ends up in a local folder, is logged with its hashes. That's a full hash plus hashes of the first, middle and last parts.
	- Every other file gets what is cheap to learn, such as its name, folder, size and dates.
	- Creating a file logs what is known about it.
	- Anything that changes part of a file's or folder's full path updates the database.

- Hashes are blake3. Reading a large file only to hash it is a last resort. The database is checked first, then the file's own attributes.

- A hash can also be written onto the file itself, in extended attributes or a Windows alternate data stream. This is a setting, off by default. See [Checksums on the files](#checksums-on-the-files).

- Tags can be added, edited and searched. They are stored in the database. With the checksum setting on, a base64url 32-bit hash of each one is also written onto the file.

- Tags, a Hidden mark and other things a person sets on a file are tattrs, short for TukzedoFS meta-attributes. See [Tattrs](#tattrs).

- A tattr says whether a file or folder inherits its parent's tattrs. It's on by default, and works like attribute and permission inheritance on Windows.

- The app works with no database at all, PostgreSQL or SQLite, with fewer features. Every feature that uses tattrs has a test case that runs it with no database.

- All of this with as little slowdown as possible. The window never waits on the database, however briefly.

- The app never visits a network share on its own to fill in the database. Only something a person does reaches a share.

- Before release, a database written by an older version is thrown away and rebuilt. After release, a change to the tables needs a migration.

- Anything that can't be rebuilt from the disk, such as tags, is exported now and then to simple files of its own. A database that is thrown away gets those back from the last export.

## Goals

- Know a file again after it's been renamed, moved or copied.

- Do slow work once. A hash or a thumbnail made for one copy serves every other copy of the same content.

- Tell real duplicates apart from one file reached by two paths. Getting this wrong is how a deduper deletes the only copy of something.

- Be the one place that dedupe, tag search, and the size totals in the compress, copy and move dialogs read from.

- Borrow the parts of WinFS that still make sense: files described by what they are, not only by where they sit, and found that way.

### Non-goals

- A real filesystem. Nothing is mounted and nothing is stored inside it. Files stay where they are, on whatever filesystem they're on.

- Needed to run. With no database, or a damaged one, the app still works. It just does some work over again, and a feature that needs tattrs goes without.

- A crawler. It doesn't walk the disk on its own to fill itself in. It learns from what the app is already doing, and from jobs someone starts, such as a duplicate search.

- A server someone has to set up. SQLite needs nothing, and PostgreSQL is only used where it's already there.

## Design

### Beside the filesystem, not under it

WinFS was Microsoft's plan for Windows Longhorn to keep every file in a relational database, described by typed properties and found by query rather than by folder. It was cut and never came out. See [Research findings](#research-findings).

- What TukzedoFS takes from it:
	- Files are records with properties that can be searched.
	- Files are tied to each other. Two paths share one content row. A thumbnail hangs off the content it was made from.
	- Tags, which put a file in more than one place without copying or linking it.

- What it leaves behind: the database under the files. In WinFS every file operation went through the store. Here the files are ordinary files on an ordinary filesystem, and TukzedoFS only watches and remembers. Other programs never know it's there, and losing it loses nothing but time. Tags are the one exception. See [Things that can't be rebuilt](#things-that-cant-be-rebuilt).

### Where it's kept

- SQLite is the default. It's one file under the user's cache folder, needs no setup, and is linked into the program.

- PostgreSQL is used when one is available and chosen in the settings. On Tukzedo Linux one is expected to be there.
	- When PostgreSQL is chosen but can't be reached, the app runs without it, as it does with no database at all. SQLite filling in for it is an option to weigh if PostgreSQL is ever added.

- Both run the same SQL. Dogfood builds and the test suite run on SQLite, so nothing may depend on a PostgreSQL-only feature unless SQLite has a path that gives the same answer.

- Each window is its own process, so several share the one database at once. Claims on shared work, such as a prune or a dedupe job, are rows taken inside a write transaction. The database's own locking decides who wins, the same way on every platform.

### What is logged when

What each thing the app does teaches TukzedoFS. "Hashed" means the full hash and the three sample hashes.

| What the app does                               | What is logged
| :---                                            | :---
| Makes a thumbnail that reads the whole file     | Hashed, while the bytes are already in memory.
| Makes a thumbnail from a preview in the file    | Hashed after the thumbnail is drawn, so the draw isn't held up.
| Copies a file, not as a clone                   | Hashed, for the source and the copy. They share one content row.
| Copies a file as a clone                        | Nothing is read. The copy shares the source's content row if the source has a fresh hash.
| Moves or renames on one drive                   | Only the path changes. A renamed folder is one row.
| Moves to another drive                          | Hashed, since it's a copy and then a delete.
| Compresses with the built-in library            | Each file that goes in is hashed.
| Compresses with 7-Zip or rar                    | Only cheap facts. The content goes to the other program, not through ours.
| Extracts with the built-in library              | Each file that comes out is hashed.
| Creates a new file or folder                    | What is known about it.
| Trashes or deletes                              | The paths go.
| Lists a folder                                  | Nothing for now. See [Rejected](#rejected).
| Runs a duplicate search                         | Hashed as far as each file needs to be. See [dedupe and thumbnails](20260925-063617_dedupe_and_thumbnails.md#finding-duplicates).

- Only a file that ends up in a local folder is hashed this way.

- A file changed by another program is noticed when its size or modified time no longer match what's stored. Its row is stale until something learns it again.

### What is known about a file

- The cheap facts: its folder and name, size, modified time, created time where there is one, and the device it's on.

- The hashes, when its whole content has passed through memory, or when a job needed them.

- Tags, once they exist.

#### Native attributes to consider

- Good attributes:
	- Canonical file path is not reliable (e.g. files and folders can be renamed and/or moved), but still an important part of early identification pass.
	- mtime and size are good, important, and reliable attributes for a first pass.

- Attributes to use with care:
	- crtime is not always available, or reliable - but can still be useful for the algorithm if that's kept in mind.

- Unreliable attributes, don't use:
	- inodes can be reused on most filesystems, and aren't even always unique between remounts (e.g. FUSE filesystems).
	- Unique device identification (a necessary part of unique inodes) is also not universally reliable across platforms and filesystems.
	- Both are still fine for comparing files within one scan, such as to find path duplicates and hardlinks. They are just not stored as identity.

### One file, many paths

- Must be critically aware of path duplicates, i.e. one file reached by more than one path. (E.g. to avoid accidentally deleting the only copy, in future dedupe work.) Such files are not actually duplicates, they're the same one file.
	- Path duplicate detection:
		- Same device and inode.
		- Same filename.
		- Parent directories also have the same device and inode.
	- Device and inode are good enough to compare within one scan. They are not kept as a file's identity from one scan to the next. See [Native attributes to consider](#native-attributes-to-consider).
	- Windows has no inode. The equivalent is the volume serial number plus the file ID.

- Hardlinks are detected and logged as such in the database: same device and inode, but a different filename or parent directory.
	- Like path duplicates, they are one file, not duplicates.
	- Hardlinks of one file are only read and hashed once.

- Symlinked folders can be followed, but the canonical path must be read and considered for the case of path duplicates.

- Must detect infinitely looped symlinked directories.

### Checksums on the files

A checksum can also be left on the file itself, in three attributes: the checksum, and the size and time it was taken at. That way it travels with the file. A copy onto another machine, or onto a drive this program has never seen, arrives already knowing what it is.

- On Linux and the BSDs they are extended attributes in the `user` namespace. On Windows they are alternate data streams, which only NTFS and ReFS have, and the setting says so where it is switched on.

- It is off by default, and switched on by a setting. Writing an attribute changes the file's ctime, which can trick poorly-written backup programs into backing up unchanged content again.
	- On Linux, the BSDs and macOS, ctime can't be reset. The kernel sets it on any attribute write, and there is no call to set it back.
	- On NTFS a write to any stream counts as a change to the whole file and moves its modified time. Left alone, that would make each checksum stale as soon as it was written, and the file would read as edited to everything else too. The write tells its handle to leave the file times as they are.

- With it on, a checksum is written when a thumbnail is made, so files already in the cache get one the next time they are drawn. A file that already carries the same checksum is left alone.

- The time is written last of the three, and reading requires both the size and the time to match. A write that stops part way then leaves the old time next to the new checksum, and the next reader throws the lot away. Written the other way round, a half-finished write leaves the old checksum under a size and time that both match, which no reader can catch.

- Writing an attribute is slow enough that it happens after the database is already up to date, never in front of a draw. A filesystem with nowhere to put one simply goes without, and the database still knows.

- Tag hashes follow the same setting. With it off, tags are only in the database and its exports.

### Tattrs

A tattr is something a person sets on a file or folder that TukzedoFS keeps, such as a tag or the Hidden mark.

- Each is kept in the database. Some also get a copy on the file, in an extended attribute, where the filesystem takes one.
	- The copy is there in case the database is missing something, and so the tattr moves with the file to another system.
	- It may not be reliable. Many copy tools drop it, and a read-only file can't take one.

- A yes-or-no tattr, such as Hidden, is set yes, set no, or not set. Not set means no answer either way, so whatever is next in line decides.

- The inherit tattr says whether a file or folder takes its parent's tattrs. It's on by default, and works like attribute and permission inheritance on Windows: what's set on a folder reaches what's inside, down to anything that turns inheriting off.
	- Whether a tag belongs to a path or to the content depends on this tattr.

- With no database, a feature that needs tattrs goes without, and the rest of the app works as usual. Each such feature has a test case for that.

### Things that can't be rebuilt

Everything in TukzedoFS can be worked out again from the disk, except what a person tells it. Those are the tattrs, and tags are the first of them. A tag hash on a file doesn't say what the tag was called, and with the checksum setting off there's no hash on the file at all.

- These are exported now and then to separate, simple files outside the database. The rest of the database has no export, since it can be rebuilt.

- A database that's damaged, or written by an older version, is still thrown away. What can't be rebuilt is read back in from the last export, so only what changed since then is lost.

- A Hidden mark kept only in TukzedoFS is another, where the file and its folder have nowhere else to keep it. See the [Properties dialog](20260930-150859_properties_dialog.md#hidden-attribute).

- The exports may be kept in git and synced: one repo for the whole machine, and one per user.
	- Not designed here: those git syncs could grow into a portable tool that syncs system and user settings, for Tukzedo Linux.

### Tables

These are planned, and replace the file cache's current tables when built. Before release there is no migration: an old database is thrown away and rebuilt, as it already is whenever the tables change.

- Tables like `dirs` may need further optimization for size.
	- E.g. Millions of entries that contain most of the same path information, would get slow.
	- For `dirs`, this is answered by storing it as a tree. Each row holds its parent and its own name, and full paths are built by walking up and cached in memory. Renaming a folder then changes one row, however much is under it.

- Rows are deleted outright when they are no longer needed, in one transaction, with cascades to the rows that hang off them.

### The file cache today

The file cache is what is built now. It is a private SQLite database under the user's cache folder, with what has been worked out about files on disk so it doesn't have to be worked out again. Thumbnails are the first thing in it and the reason it exists, but the tables are about files rather than pictures, so a checksum for a text file is as much at home there as an image is.

- SQLite is linked static. It has to come through pkg-config rather than meson's `find_library`, because the cross sysroot is not on the compiler's own search path.

- Three tables of data, plus one row of bookkeeping for pruning. `files` is one row per distinct set of file contents: the size, and the checksum once anything has bothered to compute one. It stores no image, picture or not. `paths` is one row per uri, pointing at the file it belongs to and carrying its own timestamp. `thumbnails` is only for images; it hangs off a `files` row and keeps the encoded image.

- Splitting paths from files is what lets a file that moved, or a second copy of one, find a thumbnail that is already there. It is also what a duplicate finder needs, which is why the split is drawn this way rather than around thumbnails: every file seen is a `files` row, and the copies of one are the paths hanging off it. A file nothing can draw has no `thumbnails` row and is otherwise an ordinary record.

- A checksum settles what two records that looked separate really were, so learning one folds them together. The image and every other name move onto the record that stays. Without a checksum, size and timestamp together are the only guess available, and two unrelated files that happen to match both would share a thumbnail.
	- The planned `content` table ends that guess: nothing is shared until there is a full hash.

- A record is found by its checksum alone, as the checksum is what is unique. One found at another size had its size taken before an edit, and the newer size replaces it.

- Every launch is its own process and several can be open at once, so the file is in WAL mode with a busy timeout. Writes are small and the whole store is rebuildable, so `synchronous` is NORMAL rather than FULL. A power cut can cost the last few rows, which is not worth an fsync per row.

- A damaged file, or one written by another version of the tables, is thrown away and rebuilt at open rather than migrated or repaired. Nothing in it can't be worked out again from the disk. Damage noticed while running only stops the store being used, because deleting a file other processes still have open is worse than going without until the next launch. It also leaves a marker beside the file, and the next launch starts over when it sees one. A damaged page deep in the file does not stop it opening, so without the marker nothing would ever act on it.

#### Keeping it small

- Draw counts are kept in memory and written in one transaction. Scrolling a big folder draws the same file repeatedly, and the age rule works in days, so a write per draw would buy nothing.

- Pruning runs on a worker thread over a connection of its own, so it never holds up a draw. Each pass checks the file for damage, forgets local files that are gone, drops thumbnails not drawn for too long, then drops the least recently drawn until the file is under its size limit, and last hands the freed space back to the disk.

- A file is only forgotten when its folder is still there. A whole folder missing is more often a drive that is not plugged in. Shares are skipped, and so is any folder that is slow to answer, since one that is not answering costs about twenty seconds per question.

- A pass is due at random between 4 and 24 hours after the last, and waits until nothing has been drawn for 5 minutes. All three are in the config file. Whoever finishes a pass picks the next time and writes it in the file, so every copy running agrees on it.

- Only one process prunes at a time. The claim is a row in the database, taken in a write transaction, so SQLite's own locking decides who wins. That works the same on every platform, where a lock file would need a separate answer for Windows. The claim carries a heartbeat, and one nobody has touched for ten minutes belongs to a process that died and is taken over.

- Both rules go by a thumbnail's age, the later of when it was made and when it was last drawn, and that age is indexed. Each batch is picked under the write lock, so it walks the index rather than sorting the whole table while other windows wait to write.

- The space goes back a few pages at a time with incremental vacuum rather than a full VACUUM. A full one keeps the write lock for as long as it takes to copy the whole file, and every other copy would wait on it.

- Quitting stops a pass part way through, and it lets go of its claim.

- The settings are on the Preview page: the size limit, the age limit, forgetting missing files, and saving checksums onto files. The schedule stays in the config file only. The page also shows how many thumbnails there are and the space on disk, with a button to clean up now and one to empty the cache.

- Emptying asks first, then drops every row and runs a full VACUUM. In WAL mode the VACUUM writes the new file into the journal, which then takes up more than the old file did, so the journal is folded back in and cut short after it.

### Open questions

- The exports' format, and how often they're written.

- Rows for files that still exist stay after their thumbnails are pruned, and count against the size limit. They need an age rule of their own (2026092813381437).

## Alternative ideas

### Unconsidered

Ideas that have come up but haven't been weighed.

- Saved searches shown as folders, the way WinFS planned them.

- Links between files beyond "same content", such as a file and the archive it came out of.

- Keeping the database in step between two machines.

### Rejected

- Putting the database under the filesystem, the way WinFS did. Every file operation would then depend on it. TukzedoFS sits beside the files instead.

- Keeping device and inode as a file's identity from one scan to the next. Inodes are reused, and some filesystems don't keep them across remounts.

- One full path per row in `dirs`. Millions of rows would repeat most of the same text, and renaming a folder would rewrite every row under it. A tree of parent and name was chosen.

- A graph database rather than SQL. It came up for the path problem above, which the tree answers.

- A lock file for the prune claim. It needs a separate answer on Windows. A row in the database works the same everywhere.

- `synchronous` FULL. An fsync per row isn't worth it for a store that can be rebuilt.

- A full VACUUM after each prune. It keeps the write lock for as long as the whole file takes to copy.

- Logging every file a plain folder listing shows. It's cheap to learn but not cheap to write, and a folder of 50,000 files is a lot of rows for a glance. Choices like this one are looked at again once part of TukzedoFS is built.

### Superseded

- The file cache's three tables, `files`, `paths` and `thumbnails`, are replaced by the planned tables when those are built. The old database is thrown away.

- Writing the hash onto every file that passes through memory, from the Metadata-aware item (20260923). Writing onto files became a setting, off by default, once the ctime cost was known.

- Staying with the shared freedesktop thumbnail folder. See [dedupe and thumbnails](20260925-063617_dedupe_and_thumbnails.md#superseded).

## Research findings

- WinFS was shown by Microsoft in 2003 as one of the main parts of Windows Longhorn. It kept files in a relational database built on SQL Server, with a schema for each kind of item. It was cut from Vista in 2004, had betas in 2005, and was dropped as a product in June 2006. Parts of it went into SQL Server and ADO.NET.

- Inodes are reused on most filesystems, and some, such as FUSE ones, don't keep them across remounts. A device's identity isn't reliable across platforms either.

- An attribute write sets ctime on Linux, the BSDs and macOS, and there's no call to set it back. On NTFS a stream write moves the file's modified time unless the handle is told not to.

- A prune batch of 256 thumbnails, with 40 thousand of 16 KB in the file, made another window's store wait up to about 1.4 s. Bigger thumbnails make each batch longer (2026093010493420).
